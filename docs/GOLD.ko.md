# FQ4R 골드 단위와 입력 범위

## 결론

검사한 저장·로드·표시·구매·판매·감정·획득·일부 서비스 및 전투 차감 경로에는 **저장값이 10/100의 배수여야 한다는 조건이 없습니다.** 저장값은 10G 단위입니다.

```
세이브 0x0692의 u32LE = rawGold
일반 게임 표시 금액 = rawGold × 10 G
```

| 저장값 | 파일 바이트 | 게임 표시 |
|---:|---|---:|
| 1 | 01 00 00 00 | 10G |
| 11 | 0B 00 00 00 | 110G |
| 123 | 7B 00 00 00 | 1,230G |
| 200 | C8 00 00 00 | 2,000G |
| 51,200 | 00 C8 00 00 | 512,000G |
| 999,999 | 3F 42 0F 00 | 9,999,990G |

게임 화면의 일의 자리는 항상 0이지만 십의 자리가 0이어야 하는 것은 아닙니다.

## 에디터의 단위

에디터 개요의 골드는 **게임 표시 금액 0~9,999,990G**로 표시하고 입력받습니다. 입력 간격은 10G이며, 10G 미만의 나머지는 입력 완료(포커스 이동) 시 내림 처리합니다. 예를 들어 1,230G를 입력하면 저장값은 123입니다. MAX는 9,999,990G, 랜덤은 0~9,999,990G 중 10G 단위로 선택합니다.

세이브 파서의 `summary.gold`, `editOverview({ gold })` 및 `MAX_GOLD=999999`는 원시 저장 단위를 유지합니다. UI는 `GOLD_UNIT=10`으로 변환하며 표시 상한은 `MAX_GOLD_AMOUNT=9999990`입니다. 따라서 파일을 열거나 값을 그대로 저장하는 것만으로 원시 골드값이 바뀌지는 않습니다. 변경 강조는 최초 원시값과 비교합니다.

## 조사 범위와 미확인 사항

모든 이벤트와 게임 내 상태 조합을 검증한 것은 아닙니다.

따라서 “임의의 잔액으로 절대 충돌하지 않는다”는 보장은 아닙니다. 다만 **일·십의 자리가 0이 아니어서 충돌한다는 제약의 근거는 발견하지 못했습니다.** 실제 문제가 있던 파일과 발생 시점이 있어야 다른 수정 필드, 체크섬, 이벤트 상태 등의 원인을 구분할 수 있습니다.
